# Implementation notes (PRD 23.1, 23.3)

## Deviations from the PRD
- Monorepo layout: PRD 9.3 shows a single package. The repo is a pnpm workspace with the server in
  `packages/server` (name `devworkspace-mcp`) so a later web package can sit beside it. No `apps/web` yet.
- SDK line: the PRD names `@modelcontextprotocol/sdk` (v1 line, now maintenance). The human chose the
  v2 package `@modelcontextprotocol/server` (see `OPEN-QUESTIONS.md` section 1). v1 is not installed.
- Node floor: `engines.node >=22`. OPEN-QUESTIONS Q14/Q-B: Node 22 EOL dates were unverified; SDK v2 needs
  >=20, MCP Inspector needs >=22.19. Revisit if Node 22 is confirmed EOL.
- TypeScript is pinned to `^6` because `typescript-eslint` 8.72.1 rejects TypeScript 7 ("does not support
  TS 7.0"). Move to 7 when typescript-eslint supports it.
- `@types/node` is `^22` to match the Node floor, not the newest major.
- Test layout (ADR-021): tests live in `packages/server/test/<module>/` or colocated as `src/**/*.test.ts`,
  matching the `vitest.config.ts` include. Docs that say `tests/` (doc 07) mean `test/`.
- Stdio entry (ADR-024): uses SDK v2 `serveStdio(factory)` from `@modelcontextprotocol/server/stdio`
  (one `McpServer` per connection, built in `src/server/create-server.ts`) instead of hand-wiring a
  transport. It serves both the legacy `initialize` opening and the `server/discover` opening.
- Split limit names: the PRD/doc 03 single per-page and redirect limits are split per integration:
  `githubPerPage` / `githubPerPageMax` and `maxRedirectsCustomApi` / `maxRedirectsGithub`.
- Extra file `src/config/errors.ts` (`ConfigError` with `issues: [{path,message}]`), separate from the
  loader to avoid an import cycle. Not in the PRD 9.3 tree.
- Extra config rules added by P0-03 beyond doc 03 section 2 (all fail closed at load):
  1. Endpoint `method` must be listed in its profile's `allowedMethods`.
  2. Every workspace path must resolve (realpath, symlinks followed) inside an `allowedRoots` entry.
  3. Inline secrets are rejected: unknown keys such as `token`/`password` fail the strict schema, and
     `*Env` fields must be env var NAMES (values shaped like `ghp_`, `github_pat_`, `sk-` are rejected).
  4. `github.apiBaseUrl` is the literal `https://api.github.com` (no GitHub Enterprise); custom API
     `baseUrl` and path placeholders are validated, and duplicate names are rejected.
  Also: `readOnly` must be the literal `true`; `enabled` defaults to `false`; invalid JSON errors never
  echo file content.

## Filesystem pack assumptions (P0-11, P1-01, P1-02)
- Limit override rule: `limits` overrides may only tighten the defaults. For every limit, max = default,
  except `githubPerPage`, whose max is `githubPerPageMax` (100). Config rejects larger values and
  `filesystem.createFilesystemService` re-clamps defensively.
- P1-01: encoded sequences (`%2e`, `%2f`, `%5c`, `%00`) are rejected, not decoded. Blocked matching is
  case-insensitive on all platforms. The binary sniff window (8192 bytes) and 30% control-byte threshold
  are constants, not limits. Residual TOCTOU risk between realpath and open is mitigated (O_NOFOLLOW,
  dev/ino check, second realpath) but not eliminated.
- P1-02: the workspace root (not the outer `allowedRoots`) is the containment root for every call; config
  already requires it to sit inside an allowed root. Blocked and ignored entries are hidden (not marked)
  from list/search/tree. `ignoreDirs` affect enumeration and direct access to paths inside them
  (NOT_FOUND on list/info/read); they are not a security control. `allowedExtensions` hides non-matching
  files from list/search/tree and denies reads (PERMISSION_DENIED). Symlinks appear in list/tree as type
  `symlink` only when their target is inside the root and not blocked/ignored, and are never followed or
  searched. Oversize files are read up to `maxFileBytes` and flagged `truncated` (line ranges apply within
  that window; `totalLines` is null when truncated). Content search reads at most `maxFileBytes` per file,
  skips binary and unreadable files with a warning, and stops at `maxFilesScanned` or the search deadline
  (`workflowTimeoutMs`) with `partial: true`. Non-UTF-8 text is decoded with replacement and a warning.
  Audit logging is left to the tool layer (doc 02 call flow); the service does not import core/audit.
- P1-05: the committed sample-workspace fixture holds no .env, node_modules, dist or .git; fs-tools stdio tests create them (with a fake canary) in a temp copy at test time (commit rules).

## P1-08 hardening of the filesystem pack (QA-02 backlog B1-B4)
- B1 hard links: a regular file with `nlink > 1` is refused. `PathGuard.resolve` denies it (PERMISSION_DENIED, message "File has multiple hard links and is refused by policy.", no paths) and `openFile` re-checks `nlink` on the opened handle. list/search/tree hide such files (ADR-032: hidden, not marked). Deliberate over-blocking: legitimate hard-linked files inside the root are refused too, because realpath cannot tell an outside alias from an in-root one. Directories are not affected.
- B2 backup/editor variants: every blocked pattern (built-in and `blockedNames`) also matches a segment after repeatedly stripping trailing `~`, `#name#` wrappers, and the suffixes `.bak .backup .orig .old .save .swp .swo .swx .tmp .temp .copy .rej` (vim `.name.swp` also tries the name without the leading dot). Matching stays case-insensitive. `.env.example` stays allowed; `.env.example~` and `.env.example.bak` are blocked (stricter). A trailing `~` alone does not block names whose stripped form is not blocked (`notes~` is allowed). `unblock` entries exempt the stripped name only when the raw name does not itself match a pattern.
- B3 control characters: names and relative paths returned by list, info, search and tree are escaped (`escapeName`): C0, DEL, C1, soft hyphen, ALM, Mongolian vowel separator, zero-width and bidi format characters, line/paragraph separators, invisible operators, BOM, interlinear annotation characters become `\u{HEX}` text, and a literal backslash becomes `\u{5C}` so the output is unambiguous. Guards run on the raw names before escaping. The escaped form cannot be used as input (backslashes and control characters are rejected by `parseRelativePath`), so files with such names are listable but not readable. File content and snippets are not escaped (content is not a name).
- B4 response budget: `fitToBudget` (core/response.ts) measures the serialized MCP result (structuredContent plus the text copy plus 512 bytes envelope reserve) and, when over `maxResponseBytes`, cuts array entries, text `content` or tree nodes by binary search and sets `meta.truncated`, `meta.partial`, `meta.responseBudgetBytes`, a warning, and recomputes `returnedCount`, `lines.end` and tree `counts`. The doc 04 shape is kept, so each copy carries at most about half of the budget (a max read returns roughly 95 KB of content). `toMcpResult` applies it after redaction with the default limit when no `maxBytes` is passed; the fs tool layer pre-applies the configured (possibly tighter) `limits.maxResponseBytes`. Errors and payload shapes other than array/content/tree are not cut.

## P2-01 node-sql-parser check and SQL guard (ADR-046)
- Package check (npm metadata + GitHub API, 2026-11-03): `node-sql-parser` 5.4.0, license Apache-2.0 (permissive), last npm release 2026-01-12 (about 10 months old), repository not archived, last push 2026-07-19, 84 open issues. Runtime deps: `big-integer`, `@types/pegjs`. Judged maintained enough (release cadence about every 1-3 months through 2025, active pushes in 2026). Added as `"node-sql-parser": "^5.4.0"` (caret, repo convention), lockfile updated; nothing else added.
- Real-parse findings (both dialects, version 5.4.0): parses SELECT/WITH...SELECT/UNION, INSERT/UPDATE/DELETE/DROP/CREATE/CALL/SET/REPLACE; returns two AST entries for `SELECT 1; DROP...`. Throws (so fail closed) on `FOR UPDATE/SHARE`, `EXPLAIN ANALYZE ...`, `PRAGMA`, `COPY`, `DO`, `VACUUM`, `LOAD`, `MERGE`, `DETACH` (pg), `INSERT ... ON CONFLICT`, and sqlite `BEGIN`/`COMMIT`. Gaps that needed extra code: (1) bare `VALUES` does not parse in either dialect (and not even as a subquery in sqlite); (2) PostgreSQL data-modifying CTEs (`WITH x AS (INSERT/DELETE ...)`) parse as a SELECT whose `with[].stmt.type` is `insert`; (3) SELECT INTO and `load_extension()` parse as ordinary selects; (4) pg accepts `ATTACH`/`BEGIN`/`SET`/`CALL` as statements; (5) it treats `\` in `'...'` as an escape for SQLite and handles nested comments and dollar quoting differently from the engines, so `SELECT '\'; DROP TABLE t; --'` parsed as one statement while SQLite would see two.
- Mitigations in `sql-guard.ts`: top-level type must be `select`; a full AST walk rejects any forbidden node type anywhere (insert, update, delete, create, drop, set, call, transaction, attach, explain, ...), SELECT INTO, row-locking keys, and a function denylist (load_extension, readfile/writefile, pg_read_*, pg_ls_*, lo_*, dblink*, query_to_xml family, set_config, nextval/setval, pg_terminate_backend, ...); bare VALUES goes through a strict lexical validator (literals, parentheses, commas, signs only; no ORDER BY/LIMIT/expressions after it, deliberate); an independent lexical pass rejects backslash in string literals, nested or conditional comments, dollar quoting, unterminated quotes, and any `;` that is not a trailing terminator. NUL and other control characters are rejected. All failures are `QUERY_REJECTED` with fixed text (SQL never echoed); unparseable input fails closed. Over-blocking is deliberate and listed: `pg_sleep` stays allowed (TIMEOUT test S9), `E'...'` strings and `$$` quoting are rejected on postgres too.
- Constant `MAX_SQL_CHARS` = 10000 in `sql-guard.ts` (no doc 03 limit key, like `BINARY_SNIFF_BYTES`, ADR-030); callers may pass a tighter `maxChars`. The row-cap wrapper puts the user SQL on its own lines (`SELECT * FROM (\n<q>\n) AS _dw LIMIT n`) so a trailing `--` comment cannot swallow the wrapper, drops one trailing `;`, and re-runs the lexical pass and parser on the wrapped text (a query that does not wrap cleanly, such as `SELECT 1; -- c`, is rejected). EXPLAIN builder accepts only a validated statement and emits `EXPLAIN` (pg) or `EXPLAIN QUERY PLAN` (sqlite).
- Registry (`database.registry.ts`): takes configured connections plus per-dialect adapter factories (fakes in tests); only `enabled` connections are resolvable (a disabled one is NOT_FOUND, same as unknown); the argument must match the config name pattern `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`, anything else (URL, DSN, path, whitespace) is INVALID_INPUT with fixed text and no echo; adapter factory failures become `INTEGRATION_UNAVAILABLE` with fixed text (cause kept internal), not cached. The adapter interface lives in `database.types.ts`.
- Layer 1 is advisory only: the connection-level read-only controls of doc 05 section 3 step 3 remain mandatory in P2-02/P2-03 (the parser is not a security boundary on its own).

## P2-02 SQLite adapter (ADR-046, ADR-050)
- `src/integrations/database/sqlite.adapter.ts`: `createSqliteAdapter(connection, options)`, `createSqliteAdapterFactory(options)` (registry-ready: `createDatabaseRegistry(conns, { sqlite: createSqliteAdapterFactory() })`, refuses non-sqlite or non-`readOnly` connections) and `openSqliteReadOnly(path)` (exported so tests attack the exact connection the adapter uses). Opened with `readonly: true`, `fileMustExist: true`, `PRAGMA query_only = ON`, `PRAGMA trusted_schema = OFF`; `:memory:`, `file:` URIs, NUL, directories and missing files are refused with fixed text (no path). Extension loading is never enabled (`loadExtension` is not called; `load_extension()` in SQL errors, tested).
- Empirical finding (better-sqlite3 13.0.3, SQLite 3.53): `ATTACH` is NOT blocked by the read-only connection itself (`ATTACH` of another file succeeds; the attached file inherits read-only, so writes through it fail), and `PRAGMA query_only = OFF` is accepted (`stmt.readonly` is true for both). The adapter therefore gates every statement on `stmt.reader && stmt.readonly` (non-readers such as ATTACH/DETACH/PRAGMA assignments/VACUUM/BEGIN/DML and `INSERT ... RETURNING` are refused with `QUERY_REJECTED` before execution) and better-sqlite3 refuses multi-statement strings. This second gate plus the read-only open are independent of `sql-guard` (S8 tests prove the file is byte-identical, no journal files appear).
- Timeout (S9) limitation, not fully solvable in-process: better-sqlite3 is synchronous and has no interrupt or progress-handler API, and a running native `sqlite3_step` cannot be preempted by `worker.terminate()` or a timer. The deadline (`dbQueryTimeoutMs` via `QueryOptions.timeoutMs`) is cooperative: checked after every row step and once more when the statement ends, so a query that streams rows (e.g. a recursive CTE with a selective WHERE) is aborted mid-way with `TIMEOUT` and the iterator is released, while a single very long step (e.g. `SELECT count(*)` over a huge recursive CTE) only reports `TIMEOUT` after it returns; and while a step runs the event loop is blocked (no other MCP request is served). An `AbortSignal` is honoured between rows. Options considered and rejected for now: `worker_threads` (terminate waits for the native call, risks a stuck thread and a shutdown hang), `child_process` kill (real preemption but needs a built worker script, IPC and a second read-only connection; larger than this task). Recorded in OPEN-QUESTIONS; recommended follow-up if the human wants hard preemption: a child-process executor, or a native build exposing `sqlite3_progress_handler`.
- Row cap: `maxRows + 1` detection by iterating and stopping at row `maxRows + 1` (no SQL rewriting, so `wrapWithRowCap` is not needed on the SQLite path). Cells: strings longer than `maxCellChars` (default `limits.maxCellChars`, adapter option) are cut to exactly `maxCellChars` characters ending in an ellipsis (U+2026); BLOB cells become `<binary N bytes>`; integers are read with `safeIntegers` and returned as numbers when within the JS safe range, else as decimal strings (no silent precision loss, JSON-safe).
- Catalog: `listTables` returns tables and views ordered by name, excluding `sqlite_*` internals, `schema: null`; only schema `main` (or omitted) is accepted, anything else is `INVALID_INPUT`. `describeTable` validates the identifier against `sqlite_schema` (bound parameter, then `pragma_table_info(?)` / `pragma_foreign_key_list(?)` table-valued functions with bound values; nothing is concatenated). Foreign keys with no column list (`REFERENCES parent`) are resolved to the parent's primary key. `nullable` is `NOT NULL` absent (so a non-INTEGER PRIMARY KEY column reports nullable, matching SQLite). Catalog listings are bounded by `MAX_CATALOG_ENTRIES` = 1000 (code constant, test override `maxCatalogEntries`); because `DatabaseAdapter.listTables` returns a bare array (no `truncated` channel), exceeding the bound is `LIMIT_EXCEEDED`, never silent truncation. P2-04 applies the doc 03 `maxResults` slice and `meta.truncated` on top.
- `explain(sql)` takes the validated user statement (not the `EXPLAIN`-prefixed text from `buildExplainSql`), prefixes `EXPLAIN QUERY PLAN` itself, refuses input that already starts with `EXPLAIN`, never executes the query, and returns the plan as indented text (`{ plan: string }`).
- Errors: driver `SQLITE_ERROR` and statement TypeErrors become `INVALID_INPUT` with the engine message scrubbed of the database path/file name and cut to 200 chars; read-only/auth -> `QUERY_REJECTED`; busy/locked/cantopen/notadb/corrupt/ioerr -> `INTEGRATION_UNAVAILABLE` (fixed text); nomem/toobig/full -> `LIMIT_EXCEEDED`; unexpected -> `INTERNAL_ERROR`. Cause is kept on the error object (internal only).
- Typings: `@types/better-sqlite3` 9.6.0 fits the v13 API surface used here (`readonly`, `fileMustExist`, `timeout`, `pragma`, `prepare` generics, `iterate`, `raw`, `safeIntegers`, `columns`, `reader`, `readonly`); no wrapper and no `any` needed. The package-internal `any` in its `.d.ts` is skipped by `skipLibCheck`. Gap: v13-only API additions, if any, are not typed; none are used.
- Fixture: `test/fixtures/sqlite-fixture.ts` builds a small deterministic database in a temp dir on demand (customers, products, orders, order_items with composite PK and explicit/implicit FKs, a view, an index, a BLOB and a 5000-char cell, AUTOINCREMENT for `sqlite_sequence`); nothing binary is committed. Includes `fileFingerprint()` (sha256 + size + mtime) for the S8 "unchanged" proof.

## P2-03 PostgreSQL adapter and Docker test script (ADR-046, ADR-050)
- Code: `packages/server/src/integrations/database/postgres.adapter.ts` (`PostgresAdapter`, `createPostgresAdapter(config, options)` shaped for `createDatabaseRegistry({ postgres })`). It talks to a small `PgPoolLike`/`PgClientLike` surface, so unit tests inject a fake (`test/fixtures/pg-fake.ts`) and the real `pg.Pool` is cast once at the SDK boundary. The connection string (or `passwordEnv` value) is read only through the injected `getEnv(name)` for the env var NAMED in config; an unset var is `INTEGRATION_UNAVAILABLE` with a message that names the variable, never a value. Pool: max 3, 10 s connect timeout.
- Read-only layer 2 (independent of the guard): every statement is `BEGIN READ ONLY` -> `SET LOCAL statement_timeout = <int>` -> `SET LOCAL idle_in_transaction_session_timeout = <int>` -> statement -> `ROLLBACK` in `finally`. A failed ROLLBACK or the client backstop (timeout + 2 s, or the `AbortSignal`) destroys the connection (`release(true)`) instead of reusing it.
- Single statement enforced by the server: user SQL is wrapped as ``SELECT * FROM (\n<q>\n) AS _dw LIMIT $1`` with `values: [maxRows + 1]` and `queryMode: "extended"`, so the extended protocol rejects chained statements ("cannot insert multiple commands into a prepared statement") even if sql-guard were bypassed (a `COMMIT; INSERT` breakout would otherwise leave the read-only transaction under the simple protocol). `queryMode` is a pg 8.23 per-query option that `@types/pg` does not declare and node-postgres marks "TODO: document"; the positive `values` array already forces the extended protocol, `queryMode` is belt and braces. EXPLAIN cannot take parameters, so `explain()` strips one trailing `;`, refuses any other `;` (`QUERY_REJECTED`, over-blocks `;` inside a literal on purpose) and sends plain `EXPLAIN\n<q>` (extended mode as well); never ANALYZE.
- Contract notes: `query()` receives the validated statement WITHOUT the row-cap wrapper (the adapter wraps it; callers must not pre-wrap with `wrapWithRowCap`). `maxRows` is clamped to `LIMIT_MAXIMA.dbMaxRows`. The adapter does not call `sql-guard` itself (that is the caller's duty; the Docker tests prove layer 2 holds without it). `query()` returns `PostgresQueryResult` = `QueryResult` + `cellsTruncated: boolean` (cells cut at `maxCellChars`, binary cells `<binary N bytes>`, Date -> ISO string, bigint/objects -> string/JSON string); callers should put it into `meta`. `listTablesPage`/`listRelationshipsPage` return `{items, truncated}` (cap `MAX_CATALOG_ROWS` = 500 constant, no doc 03 key); `listTables`/`listRelationships` return the items only because the P2-01 interface has no truncation channel.
- Catalog: `pg_catalog` queries, all values bound parameters; configured `schemas` is an `= ANY($1)` filter, a requested `schema` outside it is `PERMISSION_DENIED` before any query; `describeTable` resolves the name in the catalog (first configured schema in config order that has it, like a search_path) and then reads columns/PK/FK by oid; unknown is `NOT_FOUND`. Relationship table names are `schema.table`. Catalog rows are validated with zod.
- Error mapping (`mapPostgresError`, driver text never copied): 57014 -> TIMEOUT; 25006 -> QUERY_REJECTED; 42501 -> PERMISSION_DENIED; 42P01 -> NOT_FOUND; classes 28/08/53, 3D000, 25P03, 57P0x and socket/TLS codes (ECONN*, ENOTFOUND, ETIMEDOUT, ...) and connection-like messages -> INTEGRATION_UNAVAILABLE with one fixed text; other class 42 and class 22 -> INVALID_INPUT; any other SQLSTATE -> UPSTREAM_ERROR with the SQLSTATE only; else INTERNAL_ERROR. No `cause` is attached to the AppError. Logging (optional injected logger) records only the error code.
- Residual risks: a single huge cell is fully read into memory before truncation (the row cap bounds rows, not bytes); `statement_timeout` is the only preemption (the client backstop only releases the connection).
- Docker tests (ADR-046, D21): `bash packages/server/scripts/test-postgres.sh [vitest args]` (run from `packages/server`; no package.json script, that file was out of scope). It requires Docker, starts `postgres:16-alpine` (override with `DEVWS_TEST_PG_IMAGE`) on a Docker-chosen free port bound to 127.0.0.1 with random throwaway passwords, seeds `scripts/postgres-seed.sql` (customers/orders/view/numbers, `sales` and `hidden` schemas, a writing function `dw_write_probe()`, SELECT-only role `dw_ro`), exports `DEVWS_TEST_PG_URL`, `DEVWS_TEST_PG_RO_URL`, runs `test/integration/postgres.adapter.docker.test.ts`, and always removes the container (trap). Without Docker the script prints `SKIPPED: ...` and exits 0. Without those variables the Docker test file is skipped in the default `pnpm test` (one visible skipped test with the instruction). The Docker-free unit tests are in `test/integration/postgres.adapter.test.ts`.
- Security rows: S8 "data unchanged (verified)" on a real connection with the guard bypassed (writing function, `nextval`, `COMMIT; INSERT` breakout, direct INSERT, EXPLAIN chaining), S9 (more than maxRows truncated, `pg_sleep` -> TIMEOUT within seconds, pool usable afterwards, no session left idle in transaction), schema filtering, S19 (wrong password / closed port give fixed errors; canary password, host and database never appear in message, JSON or stack), read-only role.

## P2-04 db_* tools (+ P2-06 test:postgres script) (ADR-046..ADR-055)
- Tools in `src/tools/database/` (`db_list_connections`, `db_list_tables`, `db_describe_table`, `db_list_relationships`, `db_execute_readonly_query`, `db_explain_query`): registered only when at least one connection is enabled, over enabled connections only; `readOnlyHint`, no `outputSchema`; audit `resourceRef` is the connection name (or `unknown-connection`), never SQL, path, host or credentials. Inputs are `z.strictObject`; the `connection` field is bounded but lenient so the registry (not zod) decides: unknown or disabled name is `NOT_FOUND`, URL/DSN/path is `INVALID_INPUT` (S10); extra keys such as `databasePath` are refused by the schema.
- Pipeline for query/explain: `registry.dialectOf` -> `assertReadOnlySql` -> `registry.get` (adapter opened only after the SQL passed) -> adapter gets `validated.statement` UNWRAPPED (no `wrapWithRowCap`/`buildExplainSql`; adapters add the cap and the EXPLAIN prefix themselves). `maxRows` above `limits.dbMaxRows` is clamped with a warning; timeout = `limits.dbQueryTimeoutMs`.
- Truncation channel (ADR-055 follow-up): `DatabaseAdapter` gained `listTablesPage`/`listRelationshipsPage` (`CatalogPage<T>` moved to `database.types.ts`) and `QueryResult.cellsTruncated`. SQLite now offers the page variants (truncated page instead of error); its `listTables`/`listRelationships` keep throwing `LIMIT_EXCEEDED` (existing tests unchanged), tools use the page variants so both dialects behave the same: slice to `limits.maxResults`, `meta.truncated`/`partial`/`limit`, plus `rowsTruncated`/`cellsTruncated` for queries. `PostgresQueryResult` is now an alias of `QueryResult`.
- `ValidatedSql` is structural, not nominal (P2-01 note stays): only `assertReadOnlySql` output is passed to adapters in the tool layer; this is a convention, not a type guarantee.
